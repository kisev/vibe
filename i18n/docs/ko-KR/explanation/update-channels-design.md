# 업데이트 채널이 이렇게 동작하는 이유

GitHub에는 "최신 릴리스" 하나가 있습니다. Vibe는 사용자가 이전 설치에서도 전환할 수 있는 릴리스, 베타, Dev 세 라인이 필요합니다. 이 불일치가 채널 설계를 이끕니다.

## GitHub가 아니라 웹사이트인 이유

앱은 웹사이트의 `updater/<channel>.json`을 읽습니다. 각 파일은 릴리스 빌드가 생성한 `latest.json`을 다른 파일 옆에 복사한 것입니다:

- 릴리스 → `stable.json`
- 베타 → `beta.json`
- Dev → `dev.json`

채널 파일은 사이트와 함께 배포되는 정적 자산이므로, 라인을 빌드로 지정하는 것은 릴리스 편집이 아니라 커밋입니다. 또한 채널이 없을 때의 의미를 정확히 정할 수 있습니다. `404` 또는 `410`은 "이 라인에 아무것도 없음"이며 앱은 이를 최신 상태로 보고합니다. 파일이 없을 때 앱이 다른 채널로 대체하면, 후보가 없는 베타 사용자가 조용히 릴리스로 이동하게 됩니다.

## 베타 접미사가 `-rc.<n>`인 이유

시맨틱 버전은 이렇게 정렬됩니다:

```text
X.Y.Z-dev.N < X.Y.Z-rc.N < X.Y.Z
```

이 순서가 표기법의 전부입니다. 업데이터의 엄격한 비교로 Dev → 베타 → 릴리스는 항상 앞으로 이동하며, 특별한 재정의가 필요 없습니다.

이전 라인은 `-beta.N`을 사용했지만 dev 채널이 없었습니다. `X.Y.Z-beta.N`은 `X.Y.Z-dev.N`보다 위로 정렬되므로 베타 빌드가 모든 dev 빌드보다 새것처럼 보여 전환을 깨뜨립니다. 베타 채널은 이름을 유지하고 버전 접미사만 `-rc.<n>`입니다.

## 베타가 후보만 담는 이유

`X.Y.Z-rc.<n>` 버전만 `beta.json`에 기록되며 일반 릴리스는 거부됩니다. 이렇게 하면 베타 라인이 의미를 유지합니다. 두 번째 안정 라인이 아니라 후보 라인입니다. 안정 릴리스 후 베타 설치는 채널을 릴리스로 전환하면 최종으로 이동합니다. 여기서 `X.Y.Z`는 출시 후보보다 위로 정렬됩니다.

## 앞으로만 이동하는 업데이트

업데이터는 앞으로만 이동합니다. 잘못된 릴리스는 더 새로운 릴리스를 내보내 고치며, 베타 라인의 목적이 바로 그것입니다. 릴리스가 받기 전에 잡는 것입니다. Dev를 선택한 릴리스 또는 베타 설치에서 "최신 상태"가 표시되는 이유도 같습니다: 모든 dev 빌드는 이미 실행 중인 버전보다 아래로 정렬됩니다. dev 라인으로 이동하려면 dev 빌드를 한 번 직접 설치해야 하며, 그 이후에는 Dev 채널이 앞으로 업데이트합니다.

## 트레이드오프

- **복사된 매니페스트**는 채널 변경이 API 호출이 아니라 `main`에 대한 커밋과 사이트 배포임을 뜻합니다. 지연은 몇 분이며 기록을 검토할 수 있습니다.
- **채널 간 대체 없음**은 사용자가 갑작스러운 다운그레이드나 라인 간 점프 대신 정확한 "최신 상태"를 본다는 뜻입니다.
- **Dev는 한 번의 수동 설치가 필요**한 것이 시맨틱 버전 정렬을 정직하게 유지하는 대가입니다. 자동화하려면 기존 클라이언트에 없는 채널 개념이 필요합니다.
