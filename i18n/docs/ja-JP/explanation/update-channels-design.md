# アップデートチャンネルがこの仕組みである理由

GitHub の「最新リリース」は 1 つだけです。Vibe にはリリース、ベータ、開発という 3 つのラインが必要で、古いインストールからでも切り替えられる必要があります。この不一致がチャンネル設計の出発点です。

## GitHub ではなくウェブサイトを使う理由

アプリはウェブサイトから `updater/<channel>.json` を読みます。各ファイルはリリースビルドが生成した `latest.json` で、他のファイルの隣にコピーされています:

- リリース → `stable.json`
- ベータ → `beta.json`
- 開発 → `dev.json`

チャンネルファイルはサイトとともにデプロイされる静的アセットなので、ラインをビルドに向けるのはリリースの編集ではなくコミットです。また、チャンネルがないことに正確な意味を持たせられます。`404` または `410` は「このラインには何もない」であり、アプリはそれを最新として報告します。ファイルがないときにアプリが別のチャンネルにフォールバックすると、候補のないベータユーザーが黙ってリリースに移されてしまいます。

## ベータの接尾辞が `-rc.<n>` である理由

Semver の並び順:

```text
X.Y.Z-dev.N < X.Y.Z-rc.N < X.Y.Z
```

この順序がこの綴りの理由そのものです。アップデーターの厳密な比較では、開発 → ベータ → リリースが常に前方向に進み、特別な上書きは不要です。

以前のラインは `-beta.N` を使っていましたが、開発チャンネルがありませんでした。`X.Y.Z-beta.N` は `X.Y.Z-dev.N` より上に位置するため、ベータビルドがすべての開発ビルドより新しく見え、切り替えが壊れていました。ベータチャンネルは名前を保ち、バージョン接尾辞だけが `-rc.<n>` です。

## ベータが候補のみを運ぶ理由

`beta.json` に書き込まれるのは `X.Y.Z-rc.<n>` バージョンのみで、通常のリリースは拒否されます。これによりベータラインが意味を持ち続けます。ベータは候補のラインであり、2 つ目の安定版ラインではありません。安定版のリリース後、ベータのインストールはチャンネルをリリースに切り替えることで最終版に移ります。`X.Y.Z` はその候補より上に位置するためです。

## 前方向のみのアップデート

アップデーターは前方向にのみ進みます。悪いリリースは、より新しいものを出荷することで修正されます。これがベータラインの役割です。リリースが受け取る前に捕まえるのです。これが、開発を選んだリリースまたはベータのインストールで「最新です」と表示される理由でもあります。すべての開発ビルドは、すでに実行中のバージョンより下に位置するためです。開発ラインに移るには開発ビルドを 1 回手動でインストールする必要があり、その後は開発チャンネルが前方向に更新します。

## トレードオフ

- **マニフェストのコピー** は、チャンネルの変更が API 呼び出しではなく、`main` へのコミットとサイトのデプロイになることを意味します。遅延は数分で、履歴はレビュー可能です。
- **チャンネル間のフォールバックなし** は、ユーザーが驚きのダウングレードやライン間のジャンプではなく、正確な「最新です」を見られることを意味します。
- **開発には 1 回の手動インストールが必要** なのは、semver の並び順を正直に保つ代償です。自動化するには、古いクライアントにはないチャンネルの概念が必要になります。
