# 会议浏览器

会议浏览器之所以存在，是因为当 Vibe 自己承载页面时，通话更容易录制：应用控制窗口，知道录音何时进行，并能通过一个操作显示自己的浏览器界面。该设计受操作系统实际允许范围的约束。

## 为什么用 URL 方案而不是 https 点击

浏览器绝不会把 `https://` 链接交给已安装的应用，除非该应用是默认浏览器。桌面会议应用的做法则相反：它们注册自己的方案（`zoommtg://`、`msteams://`、`mattermost://`），并由自己的页面或安装程序调用它。

Vibe 也做了同样坦诚的事：

- 开启**在 Vibe 中打开会议链接**后，Vibe 会注册 Zoom、Teams 和 Webex 已在使用的会议方案（`zoommtg://`、`msteams://`、`webex://`），并将每个方案映射到它携带的 Web URL。应用会在 Rust 中验证该 URL，并在其主机允许加载时于浏览器窗口中打开，否则交给系统浏览器。
- 作为启动参数传入的 `https` URL 也走同一条路径。
- 在应用内，主页的**会议浏览器**来源和**设置 → 录音 → 在 Vibe 中打开**会把链接粘贴到同一条路径。

Vibe 有意不提供自己的 `vibe://open/` 链接：没有任何会议页面会发出这样的链接，因此当初的第一个入口已被移除。在 Chrome、Edge 或 Firefox 中点击 `https` 链接仍会打开该浏览器。让 Vibe 成为默认浏览器有意排除在范围之外：为了一个功能，它会接管机器上的每个链接，而且这仍然要由用户决定。

## 为什么内容视图是隔离的

该窗口包含两个子 webview：Vibe 的浏览器界面和远程页面。浏览器界面是应用 UI，并承载应用的能力；页面则是普通的、不受信任的 Web 内容，完全没有任何能力，不会向其注入任何脚本，摄像头/麦克风提示来自页面本身，而不是由 Vibe 代表用户授予。两者共享该进程的 WebView2 环境，因为 WebView2 不支持在一个进程中使用第二个数据目录。

浏览器界面提供地址、后退、前进、重新加载、关闭和**在系统浏览器中打开**。最后一个操作是服务拒绝在嵌入式 webview 中运行时的逃生通道。多 webview 嵌入在这里是一项桌面 Windows/Linux 能力；在 macOS 上，浏览器会回退到没有浏览器界面的纯页面窗口，而不是失败。

## 为什么浏览器是允许列表

嵌入式浏览器最初会加载页面请求的任何内容；会议主机列表只决定哪些链接会获得录制栏。现在它是一道真正的边界：只有允许的域名及其子域名可以通过 https 加载，无论是顶级页面还是它们请求的每一个资源都是如此。被拒绝的资源会得到错误响应，因此页面会把该源视为不可用，而不是永远重试。

严格是有代价的：从 CDN 拉取字体或脚本的页面在允许该 CDN 之前会一直处于故障状态。已阻止列表就是补救办法——去重后的主机，最新的在前，每个都带有**允许**操作，会添加该域名并重新加载页面。该列表绘制在浏览器界面内部，浏览器界面会随之增高以容纳它，因为在 104 像素高的 webview 中弹出窗口会被下方的页面裁剪。浏览器界面在拒绝导航时也会给出同样的提议。Windows 使用 WebView2 的 `WebResourceRequested` 强制执行资源阻止；Linux 和 macOS 目前只阻止顶级导航。

该模式是缓存的，而不是按窗口读取；资源过滤器在两种模式下都会安装，因此在 `strict` 和 `trusted-site` 之间切换后，已经打开的页面会在下一次请求时生效，而不需要重新打开。

## 为什么录音保持手动

浏览器中的每个页面都会显示**录制此会议**，并且只要有任何浏览器窗口打开，外部浏览器会议提示就会被抑制。录音仍是手动的——在通话前或通话中按下按钮，从浏览器界面或主窗口停止。自动开始会录制用户没有要求录制的通话，并会让应用的麦克风指示器在没有明确操作的情况下出现。

录音时关闭窗口会询问是停止还是在后台继续录音，因此离开通话不会悄悄丢弃或继续录音。

## 限制

- 只有已注册的会议方案或 `https` 启动参数会交给 Vibe。点击 `https` 链接需要 Vibe 不做的默认浏览器决定。
- DRM 较重或对 WebRTC 不友好的网站可能在系统浏览器中工作得更好；**在系统浏览器中打开**是受支持的回退方式。
- Windows 首先得到验证。其他平台使用各自的 webview，如果窗口无法承载通话，则回退到系统浏览器。
