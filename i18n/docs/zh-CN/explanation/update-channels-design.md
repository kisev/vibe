# 更新通道为何这样工作

GitHub 只有一个“最新发布”。Vibe 需要三条线——Release、Beta 和 Dev——用户可以在它们之间切换，包括从较旧的安装切换。这种不匹配驱动了通道设计。

## 为什么用网站而不是 GitHub

应用会从网站读取 `updater/<channel>.json`。每个文件都是发布构建生成的 `latest.json`，被复制到其他文件旁边：

- Release → `stable.json`
- Beta → `beta.json`
- Dev → `dev.json`

通道文件是随网站部署的静态资源，因此将某条线指向某个构建是一次提交，而不是一次发布编辑。它还让缺失的通道有精确含义：`404` 或 `410` 表示“这条线上没有任何内容”，应用会将其报告为已是最新版本。如果应用在文件缺失时回退到另一个通道，没有候选版本的 Beta 用户就会被悄悄迁移到 Release。

## 为什么 beta 后缀是 `-rc.<n>`

Semver 排序如下：

```text
X.Y.Z-dev.N < X.Y.Z-rc.N < X.Y.Z
```

这种排序正是该拼写的全部原因。配合更新器的严格比较，Dev → Beta → Release 始终向前移动；不需要特殊覆盖。

早期的一条线使用 `-beta.N`，但它没有 dev 通道。`X.Y.Z-beta.N` 的排序高于 `X.Y.Z-dev.N`，因此 beta 构建会显得比每个 dev 构建都新，从而破坏切换。Beta 通道保留其名称；只有版本后缀是 `-rc.<n>`。

## 为什么 Beta 只承载候选版本

只有 `X.Y.Z-rc.<n>` 版本会写入 `beta.json`；普通发布会被拒绝。这使 beta 线保持有意义：它是候选线，而不是第二条稳定线。稳定版本发布后，Beta 安装通过将通道切换到 Release 来迁移到最终版本，其中 `X.Y.Z` 的排序高于其候选版本。

## 只向前更新

更新器只会向前移动。坏的发布通过发布更新的版本来修复，这正是 beta 线的用途：在 Release 拿到它之前拦截。这也是选择了 Dev 的 Release 或 Beta 安装会看到“已是最新版本”的原因：每个 dev 构建的排序都低于它当前运行的版本。转到 dev 线需要手动安装一次 dev 构建；之后 Dev 通道会将其向前更新。

## 权衡

- **复制清单文件**意味着更改通道是对 `main` 的一次提交加上一次网站部署，而不是一次 API 调用。延迟只有几分钟，而且历史可审查。
- **通道之间没有回退**意味着用户看到的是准确的“已是最新版本”，而不是意外的降级或跨线跳转。
- **Dev 需要一次手动安装**是保持 semver 排序诚实的代价。要自动化它，就需要旧客户端没有的通道概念。
