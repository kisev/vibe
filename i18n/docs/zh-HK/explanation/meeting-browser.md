# 會議瀏覽器

會議瀏覽器之所以存在，是因為當 Vibe 自行承載頁面時，通話會更容易錄製：應用程式控制視窗、知道何時正在錄音，並可只靠一個操作顯示自己的瀏覽器介面。這項設計取決於作業系統實際允許什麼。

## 為何使用 URL scheme 而非 https 點擊

除非已安裝的應用程式就是預設瀏覽器，否則瀏覽器絕不會將 `https://` 連結交給它。桌面會議應用程式的做法相反：它們註冊自己的 scheme（`zoommtg://`、`msteams://`、`mattermost://`），並由其頁面或安裝程式呼叫。

Vibe 也同樣坦率地這樣做：

- 開啟**在 Vibe 中開啟會議連結**後，Vibe 會註冊 Zoom、Teams 和 Webex 已使用的會議 scheme（`zoommtg://`、`msteams://`、`webex://`），並將每個 scheme 對應到它所承載的網址。應用程式會在 Rust 中驗證 URL，並在主機允許載入時於瀏覽器視窗中開啟，否則交給系統瀏覽器。
- 作為啟動參數傳入的 `https` URL 會走相同路徑。
- 在應用程式內，首頁的**會議瀏覽器**來源和**設定 → 錄音 → 在 Vibe 中開啟**會將連結貼到相同路徑。

Vibe 刻意不提供自己的 `vibe://open/` 連結：沒有任何會議頁面會發出這種連結，這就是該首個進入點被移除的原因。在 Chrome、Edge 或 Firefox 中點擊 `https` 連結仍然會開啟該瀏覽器。將 Vibe 設為預設瀏覽器刻意不在範圍之內：這樣會為了服務單一功能而接管電腦上的每個連結，而且這仍然會是使用者的決定。

## 為何內容檢視是隔離的

視窗內含兩個子 webview：Vibe 的瀏覽器介面和遠端頁面。瀏覽器介面屬於應用程式的使用者介面，並帶有應用程式的能力；頁面則是普通的不受信任網頁內容，完全沒有任何能力，不會注入任何指令稿，相機和麥克風提示來自頁面本身，而非由 Vibe 代使用者授予。兩者共用該程序的 WebView2 環境，因為 WebView2 不支援在同一程序中使用第二個資料目錄。

瀏覽器介面提供網址、上一頁、下一頁、重新載入、關閉，以及**在系統瀏覽器中開啟**。最後一項操作是供拒絕在內嵌 webview 中執行之服務使用的逃生出口。多 webview 內嵌在此是桌面 Windows/Linux 的能力；在 macOS 上，瀏覽器會退回沒有瀏覽器介面的純頁面視窗，而不是直接失敗。

## 為何瀏覽器是允許清單

內嵌瀏覽器最初會載入頁面要求的任何內容；會議主機清單只決定哪些連結會取得錄音工具列。現在它是一道真正的邊界：只有允許的網域及其子網域可以透過 https 載入，頂層頁面和頁面要求的每一個資源都是如此。被拒絕的資源會收到錯誤回應，因此頁面會將該來源視為無法使用，而不是永遠重試。

嚴格是有代價的：從 CDN 取得字型或指令稿的頁面，在允許該 CDN 之前會一直故障。已封鎖清單就是補救方法——唯一的主機按最新優先排列，每個都附有**允許**操作，會加入該網域並重新載入頁面。該清單繪製在瀏覽器介面之內，而瀏覽器介面會隨之增高，因為在 104-pixel 的 webview 內彈出視窗會被下方的頁面裁剪。瀏覽器介面在拒絕瀏覽時也會提供相同的選項。Windows 以 WebView2 的 `WebResourceRequested` 強制執行資源封鎖；Linux 和 macOS 目前只封鎖頂層瀏覽。

模式會被快取，而不是每個視窗讀取一次；資源篩選器在兩種模式下都會安裝，因此在 `strict` 與 `trusted-site` 之間切換，會在已開啟的頁面下一次發出要求時生效，而不需要重新開啟。

## 為何錄音保持手動

瀏覽器中的每個頁面都會顯示**錄製此會議**，而且只要有瀏覽器視窗開啟，外部瀏覽器的會議提示就會被抑制。錄音仍然是手動的——在通話前或通話期間按下按鈕，從瀏覽器介面或主視窗停止。自動開始會錄下使用者沒有要求錄製的通話，並會在沒有明確操作的情況下讓應用程式的麥克風指示燈出現。

錄音期間關閉視窗時，會詢問要停止還是繼續在背景錄音，因此離開通話不會在無聲無息中捨棄或繼續錄音。

## 限制

- 只有已註冊的會議 scheme 或 `https` 啟動參數會交給 Vibe。`https` 點擊需要 Vibe 不會作出的預設瀏覽器決定。
- 大量使用 DRM 或對 WebRTC 不友善的網站，在系統瀏覽器中可能運作得更好；**在系統瀏覽器中開啟**是支援的退回方式。
- Windows 是首先驗證的平台。其他平台使用自己的 webview，若視窗無法承載通話，便退回系統瀏覽器。
