# 更新頻道為何如此運作

GitHub 只有一個「最新發行版本」。Vibe 需要三條版本線——正式版、Beta 和 Dev——讓使用者可以切換，包括從較舊的安裝切換。這種落差推動了頻道設計。

## 為何使用網站而非 GitHub

應用程式會從網站讀取 `updater/<channel>.json`。每個檔案都是發行構建版本產生的 `latest.json`，並複製到其他檔案旁邊：

- 正式版 → `stable.json`
- Beta → `beta.json`
- Dev → `dev.json`

頻道檔案是隨網站部署的靜態資源，因此將版本線指向某個構建版本是一項提交，而非發行編輯。它也讓缺失的頻道有精確的含義：`404` 或 `410` 代表「此版本線沒有內容」，應用程式會回報為已是最新版本。如果應用程式在檔案缺失時退回另一個頻道，沒有候選版本的 Beta 使用者便會在無聲無息中移至正式版。

## 為何 beta 後綴是 `-rc.<n>`

Semver 排序：

```text
X.Y.Z-dev.N < X.Y.Z-rc.N < X.Y.Z
```

這種排序正是如此拼寫的原因。使用更新器的嚴格比較，Dev → Beta → 正式版永遠向前推進；毋須特殊情況的覆寫。

較早的版本線使用 `-beta.N`，但當時沒有 dev 頻道。`X.Y.Z-beta.N` 的排序高於 `X.Y.Z-dev.N`，因此 beta 構建版本會看起來比每個 dev 構建版本更新，並破壞切換。beta 頻道保留其名稱；只有版本後綴是 `-rc.<n>`。

## 為何 beta 只包含候選版本

只有 `X.Y.Z-rc.<n>` 版本會寫入 `beta.json`；普通發行版本會被拒絕。這令 beta 版本線保持有意義：它是候選版本線，而非第二條穩定版本線。穩定版本發行後，Beta 安裝可透過將其頻道切換到正式版來移至最終版本，因為 `X.Y.Z` 的排序高於其候選版本。

## 僅向前更新

更新器只會向前推進。不良發行版本可透過發行更新的版本來修復，這正是 beta 版本線的用途：在正式版取得之前先捕捉它。這也是選擇 Dev 的正式版或 Beta 安裝會看到「已是最新版本」的原因：每個 dev 構建版本的排序都低於它已執行的版本。轉到 dev 版本線需要手動安裝一次 dev 構建版本；之後 Dev 頻道便會將其向前更新。

## 取捨

- **複製的清單**意味著頻道變更是對 `main` 的提交加上網站部署，而非 API 呼叫。延遲是數分鐘，而歷史可供審閱。
- **頻道之間沒有退回機制**意味著使用者會看到準確的「已是最新版本」，而非意外的降級或跨版本線跳轉。
- **Dev 需要手動安裝一次**是保持 semver 排序誠實的代價。自動化它需要舊用戶端沒有的頻道概念。
