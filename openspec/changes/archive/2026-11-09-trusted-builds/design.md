# Design

## Context

Signing today is a binary flag: `release.yml` input `sign-windows` routes through a remote YubiKey sign server (cloudflared tunnel + `scripts/sign.py serve`) whose credentials do not exist on this host. The updater's minisign keys are set and work. The user's constraint is explicit: free options only; the Apple Developer Program is rejected on principle, so macOS notarization is out of scope permanently.

## Decisions

- **Provenance first, certificates second.** Attestations, SBOM, and artifact scanning are free today, need no external approval, and raise trust for every platform including Linux. They land before any provider work.
- **Attestations via GitHub's built-in `actions/attest-build-provenance`.** No new accounts; verification is `gh attestation verify <file> -R kisev/vibe`. Works for the tauri bundles because they are files the workflow produced.
- **SBOM: syft per bundle, uploaded to the release.** SPDX format, one file per platform artifact set. Trivy reads the SBOM too, so the scan covers the dependency graph, not just file bytes.
- **Provider switch as a workflow input enum**, not three workflows: `sign-windows: none | self-signed | signpath | sign-server`. Each provider is a job step behind the same contract (sign in place, verify with `osslsigncode verify` where applicable). The existing sign-server path keeps its name and secrets.
- **Self-signed fallback:** a repo-generated self-signed Authenticode cert committed nowhere, its fingerprint documented. Windows users trust it once; it removes "Unknown publisher" while remaining honest about the chain. Generated by a task (`task release:selfcert`) and stored as a repo secret so CI can use it.
- **SignPath Foundation:** application is a human step (public repo, project description). The workflow side is pre-wired behind `signpath` using their GitHub Action and repo secrets (`SIGNPATH_API_TOKEN`, project id); nothing breaks until approved.
- **macOS:** documented bypass only. No ad-hoc games beyond what tauri already does.
- **Relationship to `fork-update-sources` 4.1:** that task needs a signed release to prove the in-app update end to end. `self-signed` is enough to exercise the update flow (minisign covers authenticity of `latest.json`), so 4.1 can close on a self-signed run before SignPath approval.

## Risks / Trade-offs

- [Attestation availability on forks] → attestations work on public repos with Actions; verify on the first dev build before relying on them.
- [Self-signed still warns] → true; it is a stepping stone, documented as such, replaced by SignPath when approved.
- [Trivy noise on the C/C++ engine] → tune ignore rules explicitly in `trivy-release.yaml`; never disable the whole scanner.

## Migration Plan

One PR adds the attestation/SBOM/scan job and the provider switch with `none` and `self-signed` live, `signpath` dormant. The SignPath application happens in parallel out-of-band; when approved, set secrets and flip the input.

## Open Questions

- Should attestations also cover dev builds or only stable releases? (Cost is nil; noise in the dev flow is the only concern.)
